## Spec 013 — Subscription Owner

### Points solides

- Le socle `Subscription` existe déjà via `009`.
- Le besoin owner est lisible: consulter trial, plans, fonctionnalités, pas de paiement immédiat.
- `vercel.json` contient déjà `/api/internal/check-subscriptions`, ce qui est cohérent avec l'infrastructure décrite.

### Risques

- La spec demande `Plan` et `PlanFeature`, mais le schéma actuel n'a que `Subscription.plan` en string.
- Elle dit "Stripe intégré mais inactif" alors que `ADR-005` parle Stripe Connect pour marketplace/commissions. Il faut séparer abonnement owner simple et Stripe Connect merchant/réservations.
- `Out of Scope` dit "Abonnement Merchant (spec 016)", mais `016` est superadmin, pas billing merchant.
- Le cron est défini dans la spec alors que la règle projet impose la centralisation dans `vercel.json`; la spec doit seulement référencer le cron centralisé.
- La grille tarifaire contient des fourchettes de prix (`9-19`, `29-49`, `99-299`) non exploitables contractuellement.

### Amendements intégrés le 2026-05-24

- Statut passé de `draft` à `review`, puis `approved` après validation PO.
- Décision PO: garder `Subscription.plan` string, ne pas créer `Plan` / `PlanFeature` en MVP 2.
- Décision PO: plans affichés via tableau statique typé côté code.
- Décision PO: prix indicatifs non contractuels.
- Décision PO: aucun appel Stripe en MVP 2 — pas de Checkout, Customer Portal, webhook ni Customer Stripe.
- Référence abonnement Merchant corrigée vers une future spec billing merchant dédiée, pas `016`.
- Cron clarifié comme centralisé dans `vercel.json`.

### Décision

Validée par le Product Owner. Prochaine étape: implémentation tests + code + traceability selon `AGENTS.md`.

## Spec 014 — Auth Merchant

### Amendements intégrés le 2026-05-24

- Statut passé de `draft` à `review`, puis `approved` après décision PO.
- Source de vérité du rattachement Merchant ↔ POI fixée : `MerchantProfile`.
- `MerchantClaim` reste la demande vérifiable, pas le rattachement durable.
- Validation/rejet admin minimale incluse dans `014` pour débloquer l'onboarding, sans attendre le dashboard super-admin complet.
- `deleted_at` ajouté à `MerchantClaim` et `MerchantProfile`.
- Règles de transition ajoutées : `pending -> approved` ou `pending -> rejected`.
- Un Merchant ne peut avoir qu'une claim `pending` et qu'un `MerchantProfile` actif en MVP 2.
- Un POI déjà rattaché à un `MerchantProfile` actif n'est plus revendicable.
- Recherche POI cadrée : actifs, non supprimés, non rejetés géographiquement, non rattachés.
- Contrats d'erreur API ajoutés pour `401`, `403`, `404`, `409`.

### Points solides

- Compatible avec `009`: rôle `merchant`, routes `/merchant/*`, redirection post-login.
- Périmètre utile: onboarding + claim d'un POI existant.
- Aligne bien `MerchantClaim` avec `ADR-007`.

### Risques restants

- La validation admin est minimale dans `014`; le dashboard super-admin complet devra l'absorber ou l'étendre plus tard.
- Les contraintes "une seule claim pending" ne sont pas exprimables en index unique partiel Prisma portable ; elles devront être garanties par transaction applicative et tests.
- `015-dashboard-merchant` devra réutiliser exclusivement `MerchantProfile`, pas `MerchantClaim`, pour charger la fiche du Merchant.

### Décision

Validée par le Product Owner. Prochaine étape: démarrer tests + code + traceability selon `AGENTS.md`.

## Spec 015 — Dashboard Merchant

### Points solides

- Bon découpage métier: profil, photos, stats, offres.
- Réservations explicitement hors scope, cohérent avec la stratégie de ne pas ouvrir cette verticale trop tôt.
- Compatible avec `ADR-007`: offres et profil doivent être extensions du POI public.

### Amendements intégrés le 2026-05-24

- Statut passé de `draft` à `review`, puis `approved` après validation PO.
- Dépendance à `014-auth-merchant` clarifiée: toutes les routes chargent le POI via `MerchantProfile.status = active`.
- Champs POI éditables limités à `name`, `description`, `hours`, `phone`, `website`, `photos`.
- Champs sensibles explicitement non éditables: ville, catégorie, sous-catégorie, adresse, coordonnées GPS, rating, géocodage et review source.
- Upload photo cadré: bucket Supabase Storage `merchant-poi-photos`, formats `jpeg/png/webp`, 5 MB max, 5 photos max.
- Suppression/réordonnancement de photos laissés hors scope pour éviter de modéliser prématurément une galerie avancée.
- `MerchantOffer` défini comme extension du POI, avec `deleted_at`, `is_active`, `ends_at`, limite 3 offres actives non expirées.
- Expiration d'offre clarifiée: masquage par query publique, pas de cron.
- Stats 30 jours cadrées sur `Analytics.poi_id` et les événements `poi_click`, `phone_click`, `directions_click`, `website_click`.
- Contrats API détaillés pour `/api/merchant/profile`, `/api/merchant/photos`, `/api/merchant/stats`, `/api/merchant/offers`, `/api/merchant/offers/{id}`.
- Intégration publique précisée: fiche POI affiche photos mises à jour, offres actives, et enregistre les événements nécessaires.

### Risques restants

- `PointOfInterest.photos` reste un tableau de chaînes: suffisant pour MVP 2, mais une future galerie avec suppression/réordonnancement nécessitera un modèle dédié.
- `website_click` n'existe pas encore dans les implémentations publiques actuelles; `015` devra l'ajouter avec tests.
- Les modifications Merchant sont sans validation admin par choix métier; le risque qualité est borné par la liste stricte de champs éditables.

### Décision

Validée par le Product Owner. Implémentation autorisée selon `AGENTS.md`.
